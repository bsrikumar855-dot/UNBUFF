# Product lens
Score: 5 | Vote: FUND IF

## What is strong
- There is a real point of view: evidence over claims. Self-reported or stand-in-judge results never count as verified, and the study plan is built only from verified records. That one rule is a clear identity, and it is rare to see a product refuse to flatter its user.
- Craft in places users cannot see: server-graded quizzes, deletable mentor memory, a mentor that never invents statistics, a security audit done, CI green. These suggest care that will also show where users can look.
- The interview audit (interrogating resume claims, report, retest) is a distinctive moment a student can describe to a friend.
- The pieces connect: audit, plan, practice, resume feed one another, which is the start of owning the whole experience.

## What would kill it (the top 3, most dangerous first)
1. No focus. The brief lists a planner, audit, DSA catalogue, code workspace, 27 patterns, 12 DBMS topics, mentor, GitHub insights, LeetCode import, job matching and a LaTeX resume builder. The pitch does not fit in one sentence. A single student built all of it, so each part is likely thin, and many competing tools plausibly cover each part (I have no data on this; it is an open question).
2. The core promise is not yet deliverable. Code judging needs an execution service that is not deployed, the resume PDF compiler is development-only, and the company-wise question list has no licence. The feature the evidence loop depends on (verified code results) does not run, so the "verified" plan has little verified input today.
3. The first five minutes are unknown and probably harsh. A new student has no verified evidence, so the plan is empty by design. Free-tier hosting that sleeps when idle adds a slow first load. Nothing is deployed to production, so no real student has had a first session.

## The questions I would ask the founder
- Say what the product does in one sentence. Which single feature would you keep if you had to delete the rest?
- Walk me through minute one to minute five for a student with no history. What do they see, and what makes them come back tomorrow?
- If the evidence is thin on day one, what does the student get before any verification exists?
- Which features have you watched a real student use? What did they get stuck on?
- Does the strict "unverified does not count" rule frustrate students who just want a plan? How do you know?
- What would you cut first, and what does the product lose when it goes?

## If FUND IF: the conditions
- Pick the one thing (likely the audit-to-verified-plan loop) and demote or remove the rest from the main path before launch.
- Get code judging live, or ship without it and say so plainly, so the verified loop works end to end.
- Deploy to production and watch at least a handful of real students through their first session; report where they stalled.
- Define the empty-state first session so the first five minutes deliver value without prior evidence.
- Resolve the licence gap by removing the company-wise question list from anything user-facing until licensed.
